# 2.0 plan

Status: draft. Nothing here ships in 1.x. [stability.md](stability.md) lists what a major version is allowed to break; this page picks what to break and how to keep migration painless.

## Goals

- Drop the compatibility shims 1.x carries only because stability.md forbids removing them.
- Make `country` machine-readable, so country-scoped brokers (`countries:` in `brokers.yaml`, added in 1.8) don't depend on free-text matching.
- No manual migration for a normal setup: every removed format is rewritten on first load, and the release notes list the rest.

## Breaking changes

| # | Change | Today | 2.0 | Migration |
|---|---|---|---|---|
| 1 | Legacy `profile:` block | `normalizeProfiles`, `DefaultProfileID` fallback in `GetProfiles` | Only `profiles:` is read | Rewritten as `profiles: [{id: default}]` on first load of a 1.x config; in-memory fallbacks go |
| 2 | `email.provider` | Only `smtp` accepted, empty allowed | Key removed (SMTP is the only transport) | Ignored and dropped on save, like `pipeline.auto_confirm` today |
| 3 | `monitor --once` | No-op, prints deprecation | Flag removed | None; the behaviour is the default |
| 4 | `country` as free text | Resolved by `dpa.ForCountry` and `countryAliases` ("UK", "Holland", ...) | ISO 3166-1 alpha-2 code | On first load, resolve the old value through the alias table once and store the code. Unresolvable values keep a warning and stay unscoped (never hide brokers) |
| 5 | Template/evidence country display | Prints the profile's `country` string | Prints the country name looked up from the code | None for users; templates using `{{.Country}}` get the name |

Not breaking, but done in the same release because they touch the same code:

- One `Broker.Domains()` replacing three hand-rolled URL-to-domain helpers (`cmd_confirm.go`, `cmd_fill.go`, `inbox/monitor.go`).
- One region predicate shared by `broker.Filter` and the web broker list.

## Out of scope

- `history.db` schema, `brokers.yaml` fields and `export --format json` fields stay as they are; none of the above needs touching them.
- The web UI and `eraser mcp` are outside the stability contract and can change in any release.

## Open questions

1. Should the one-time config migration write a `config.yaml.1x.bak` before rewriting? Cheap and reversible; leaning yes.
2. Keep reading the old `country` alias table forever as the migration path, or only until 2.1? Leaning until 3.0, since it's data, not code on a hot path.
3. Should setup's country field become a dropdown of ISO codes, or keep free text and resolve on save? Dropdown makes bad values impossible; free text is friendlier for the CLI `init` prompt.

## Order of work

1. ISO country (4, 5): biggest user-visible change, and the migration pattern the rest reuse.
2. Remove `profile:` and `email.provider` (1, 2) behind the same migrate-on-load.
3. Remove `--once` (3) and land the two dedupes.
4. Update stability.md, commands.md and the CHANGELOG migration notes; release as 2.0.0.

Each step is its own PR; the release-please major bump comes from a `feat!:` / `BREAKING CHANGE:` commit on the first step that actually breaks something.
